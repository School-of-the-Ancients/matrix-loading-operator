# Reviewed generator development in the existing Agent Portal

This check used the built `/web/` Matrix runtime and the existing persistent Agent Portal at `127.0.0.1:19864`, with separate `work/generator-path-state` scenes, assets, and Python environment. It did not touch the user's service, world, registered assets, or Blender installation. The browser reported `matrix-web` / `threejs-webxr` in desktop presentation. The [initial screenshot](generator-before-browser.png), [six-step screenshot](generator-after-browser.png), [eight-step screenshot](generator-revised-browser.png), [post-restore screenshot](generator-post-restore-browser.png), [receipt and scene trace](generator-development-browser.json), and [post-restart trace](generator-development-after-restore.json) are from this isolated run.

The first typed Agent Portal turn found an empty world, two loaded generators (`bridge` and `curved-bench`), no `staircase`, and no registered GLB assets. It made no changes. A separate reviewed Codex coding task then added `staircase@1.0.0:staircase-v1` to the existing registry (`10de56f`), with individually indexed closed treads and the same generic create/update path. The browser still advertised only the two old generators until the new build was loaded. This source edit used the normal repository review path: the Portal cannot approve a native file-change request in its browser panel. The same saved Portal conversation resumed after browser reload, rediscovered the new generator, and used generic procedural tools without a per-object endpoint or Blender export.

Review found that the initial staircase metadata advertised any number while generation required a whole step count. Commit `099cc8d` added a bounded integer parameter type to both WebRuntime and ControlService. The PC service now rejects fractional steps before create/update queueing and named checkpoint writes; ordinary fractional dimensions on the existing generators still work. The service restart and final browser reload above used this fixed code. A read-only review found no remaining defect in the scoped generator/contract changes.

WebRuntime passed **453/453** tests and Vite built successfully; the full ControlService suite passed **739/739** tests. Source tests cover stale/invalid/over-budget recipes, independent instances, Undo/Redo, browser save/reopen, and Rapier static-mesh contact at low and high treads. An eight-step staircase measured 8 parts, 192 vertices, 96 triangles, and 3,456 geometry buffer bytes. In 1,000 warmed Node `generateProcedural` runs after 20 warmups, median generation was **0.182 ms** and p95 **0.445 ms** on this PC. These are local generation timings, not headset frame times. [The separate repeated-regeneration check](procedural-regeneration-metrics.md) covers shared-resource disposal for bridge and bench instances.

The [curved-bench browser trace](Procedural-Citizens-Desktop-2026-09-26.md) separately observed a generated static object's reviewed rest interaction completed by a resident, including recipe revision, save/reopen, and PC restore. This staircase run establishes rendered geometry and a source-level Rapier mesh-contact test; it does not establish live player/resident stair traversal. Requests were typed; no Quest wearer, spoken input, physical-room alignment, elevated bridge traversal, or resident-initiated construction was tested. The browser's scene has no rigid body/collider scope for the Agent-authored staircase, so the visible staircase alone is not a live collision claim.
