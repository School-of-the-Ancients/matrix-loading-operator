# AI Citizens in the Matrix Web world

The [#20](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/20) shared-world slice builds on the isolated [Citizens desktop fixture](Citizens-Desktop-Demo.md). The ordinary `/web/` page has an opt-in **AI Citizens** panel. It runs the same two-resident simulation through the page's existing `MatrixWorld`, `MatrixView`, and `MatrixBridge`. **Start here** creates the original chair/table/two-orb fixture only on an empty desktop virtual floor. The selected-station path keeps an existing scene and binds one selected built-in chair/table or a registered static GLB with a reviewed interaction while adding two orb residents. The Agent Portal is not used for resident decisions or given to residents. The [#19](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/19) candidate adds the finite social session described below to the reservation lifecycle.

## Reviewed registered GLB station candidate

This [#15](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/15) slice makes **one existing, registered static GLB** usable as a Citizens rest or eat station on the desktop virtual floor. The version-1 descriptor belongs to the scene object, not just its asset name. It binds the exact GLB SHA-256, kind, local approach and use poses, range, duration in simulation ticks, capacity one, and bounded need effect. The PC validates and queues `set_interaction` or `remove_interaction` with the latest observed transform and prior descriptor as preconditions; the prior descriptor may be null on first set. The browser checks the currently rendered object's measured bounds, pose, clearance and expected command state before returning a receipt. Citizens chooses and reserves the station, routes to its transformed approach pose, and applies the effect only after a matching finite `MatrixWorld.interact` outcome. A saved scene retains the descriptor and object ID; the nested Citizens checkpoint is v6 while the outer world envelope remains v3. Browser reload requires a fresh renderer measurement before another use. Built-in chair/table interactions and older Citizens checkpoints remain supported.

The original [demo chair GLB](../WebRuntime/test/fixtures/citizens-demo-chair.glb) has [editable generator source](../WebRuntime/test/fixtures/build_citizens_demo_chair.py) and a [reviewed rest descriptor](../WebRuntime/test/fixtures/citizens-demo-chair-interaction.json). It is a small static prop with no clips or external assets. To reproduce in a **new isolated** directory and free port, build WebRuntime and register the exact GLB bytes before starting the service:

```powershell
npm.cmd --prefix WebRuntime ci
npm.cmd --prefix WebRuntime run build
$demoRoot = Join-Path $env:TEMP 'matrix-citizens-authored-seat'
$scenes = Join-Path $demoRoot 'scenes'
$assets = Join-Path $demoRoot 'web-assets'
New-Item -ItemType Directory -Force -Path $scenes,$assets | Out-Null
$bounds = '{"center":{"x":0,"y":0.475,"z":0},"size":{"x":0.62,"y":0.95,"z":0.62}}'
python ControlService/register_web_asset.py WebRuntime/test/fixtures/citizens-demo-chair.glb --name 'Citizens Demo Chair' --description 'Static chair; front faces negative Z' --spawn-scale 1 --local-bounds $bounds --catalog $assets
python ControlService/server.py --host 127.0.0.1 --port 19850 --scenes $scenes --web-assets $assets
```

Open `http://127.0.0.1:19850/web/` in a fresh browser origin and wait for **Operator connected**. In another PowerShell session at the repository root, queue this bounded `spawn` for the registered `web:citizens-demo-chair:fb5408949487` asset on `web-floor` at `(0, 0, -2)`:

```powershell
$base = 'http://127.0.0.1:19850'
$spawn = @{op='spawn';assetId='web:citizens-demo-chair:fb5408949487';anchorId='web-floor';transform=@{position=@{x=0;y=0;z=-2};rotation=@{x=0;y=0;z=0};scale=@{x=1;y=1;z=1}}} | ConvertTo-Json -Depth 10
Invoke-RestMethod -Method Post "$base/api/command" -ContentType 'application/json' -Body $spawn
```

Wait for the model to render and confirm the **applied browser receipt**; the POST only queues the command. Ask the PC `matrix_set_interaction` tool to attach the fixture descriptor, or queue the following exact bounded command on this isolated service. Again, confirm its applied browser receipt before using the station:

```powershell
$state = Invoke-RestMethod "$base/api/state"
$chair = @($state.snapshot.scene.objects | Where-Object assetId -eq 'web:citizens-demo-chair:fb5408949487')
if ($chair.Count -ne 1) { throw 'Expected exactly one registered chair' }
$interaction = Get-Content WebRuntime/test/fixtures/citizens-demo-chair-interaction.json -Raw | ConvertFrom-Json -AsHashtable
$body = @{op='set_interaction';objectId=$chair[0].objectId;interaction=$interaction} | ConvertTo-Json -Depth 10
Invoke-RestMethod -Method Post "$base/api/command" -ContentType 'application/json' -Body $body
```

Click the rendered chair in `/web/`, enter a reproducible seed, choose **Use selected station**, and **Step** once to see one resident claim it and the other wait. **Run** until both complete a rest, then pause, save a named **PC world checkpoint**, reload the same browser origin, wait for the GLB to render again, and resume. The panel shows needs, claims, current activities and a decision/action log. An absent descriptor, different asset hash, animation clips, moving target, blocked approach/use lane or mismatched receipt stops the relevant action without the advertised benefit. The exact isolated browser record is linked from [Current Checkpoint](Current-Checkpoint.md). This is bounded desktop virtual-floor behavior; general animated interactions, moving furniture, room AR alignment and Quest wearer acceptance remain open.

## Changed-route recovery candidate

The `codex/citizens-route-recovery` branch adds a bounded recovery rule for an active individual trip on the desktop virtual floor. `MatrixWorld` derives a navigation geometry identity from current scene objects, transforms, asset signatures and renderer verification, excluding the resident orbs' own observed motion. When an authored obstacle changes, Citizens reports a replan and routes again from the current observed pose. A temporary blocked route keeps the same activity execution and any station claim for up to three retry ticks. If the route clears, it continues; if it remains blocked on the following attempt, the activity fails, releases any claim and grants no need benefit. Successful moves still need swept clearance and MatrixWorld receipts. This covers static, floor-aligned geometry; it does not make animated obstacles or independently moving bodies navigable. Social-session travel still interrupts immediately on an unavailable route and is outside this retry slice.

## Try it safely


Open `http://127.0.0.1:19840/web/` in a separate browser profile with no saved world for that origin. Choose a seed and click **Start here** in the AI Citizens panel, then **Run** or **Step**. The panel shows each resident's need levels, activity, recent outcome, reservations, social session, relationship, and decision log. **Stop Citizens** requires a second click within ten seconds; it removes the simulation state but leaves its objects in the scene. Existing worlds cannot start this fixed-position scenario until the user explicitly chooses a separate empty world.

For the original selected-furniture candidate, use the ordinary `/web/` desktop virtual room with an existing built-in chair or table, select that object, then choose **Use selected station** in the AI Citizens panel. This is an explicit alternative to **Start here**: it does not clear the existing scene, move or duplicate its furniture, or start the separate `/web/citizens.html` fixture. It adds two ordinary orb residents and binds the selected object's existing ID as a rest or food station. The reviewed-GLB extension above uses this same path; visual resemblance alone does not qualify a GLB. Existing scene objects remain. Finish or remove an active game before starting Citizens.

The selected path is bounded to the desktop virtual floor. It refuses an absent or incompatible selection, an already active Citizens simulation, an active game, moving or unsupported scene geometry, and placement or movement that cannot meet the current room and clearance limits. Residents travel by finite, observed MatrixWorld moves; a blocked or unreachable route is reported instead of crossing known obstacles or granting the expected need benefit. The capacity-one claim, wait, timeout, cancellation, and matching interaction receipt rules still apply. Browser reload and named PC whole-world restore carry the scene object IDs and Citizens state together; restore validates the saved bindings before replacing the active world. The panel log and feedback show refusals and interrupted actions. These are candidate behavior descriptions, not new Quest wearer evidence.

Navigation uses current measured footprints on one level virtual floor. The two orb residents retain their 0.7 scale; resizing or elevating one makes its binding incompatible with the fixed clearance calculation. Selected furniture and other scene objects must be floor-aligned, upright, and have stable measured bounds. Registered GLBs additionally require current renderer measurement. V4 exploration goals are local to each resident and bounded by the virtual floor; older checkpoint versions retain their original narrower target bounds during validation. An unavailable route fails explicitly, and the panel performs its full route search only after **Use selected station** is clicked.

## Earlier reservation lifecycle candidate (#19)

This earlier slice used a **version 3** scene/game/Citizens envelope and **`schemaVersion: 2`** nested Citizens checkpoint. It added `actionSequence` and `retiredResidentIds`; each active activity has an `executionId`. Each capacity-one station stores `claim: {residentId, executionId, expiresTick}` or `null` and a FIFO `waiters` array of `{residentId, executionId, enqueuedTick}`. The panel shows the claim's execution and expiry, each waiter's queue position and execution, and retired actors or removed fixture resources.

A claim lasts at most **72 simulation ticks** from acquisition. If it expires, that execution fails and releases its claim; a waiting resident can take the next free turn. The head of a station's queue goes first, in deterministic enqueue tick and execution order. A wait expires after **96 ticks**. Cancellation, failed movement or interaction, and AR entry clear the affected claim or wait without granting a need benefit. A station is checked again at use time; only a matching `MatrixWorld` interaction outcome updates the need. These are local simulation ticks, displayed as minutes in the panel, not wall-clock minutes or a PC-service lease.

Deleting a live resident object retires its ID, cancels its activity or wait, and frees its claim. Deleting a station object removes that station and cancels its claimant and waiters. Other residents can keep running on remaining activities and stations; deleting the last resident pauses Citizens. A still-present incompatible object or active transform owner requires recovery; an externally moved compatible object pauses the simulation for inspection. Restoring a checkpoint whose named bindings are missing or incompatible is rejected before replacing the active world. The runtime reconciles a live deletion into a valid Citizens snapshot before saving the edited world, including edits made while the virtual world is paused in AR.

On browser restore, a valid nested **v1** Citizens state migrates deterministically: resident order assigns execution IDs to active activities, each old `holder` becomes a matching claim with expiry at the saved tick plus 72, and wait/retired lists begin empty. At the earlier reservation/social checkpoint, browser restore migrated valid v1 and v2 states through the intermediate versions to nested v4. A v3 state requires retained completed events consistent with its relationship score before migration. The current browser continues through v6, while the PC service accepts v1 through v6 checkpoint shapes and preserves an older raw file until browser restore migrates it; it does not rewrite the old file in place. A scene/game-only version 2 world envelope remains scene/game-only.

At this earlier checkpoint, the start flow was still a fixed two-resident, two-station fixture on an empty desktop floor. The v2 validator bounds live plus retired residents to four, live stations to two, and the log to 80 entries. Each activity acquires at most one resource. This earlier checkpoint predates the v3 social session and selected-furniture candidate above; general multi-resource acquisition remains open. Quest simulation and multiplayer networking remain separate work.

## Reservation lifecycle verification

The first edit that removes a bound resident or station also stores the complete prior browser world in a separate **pre-deletion recovery** slot before normal autosave. This covers Delete, Clear, and scene Load. If that backup cannot be verified, both autosave copies stay at their previous values and the page reports the failure. The Citizens panel shows the backup minute and offers **Restore** with a second confirming click; restore validates the full saved world before replacement. After the restored world is saved durably and verified, the slot clears so a later deletion can capture a fresh copy. The manual **Save world** checkpoint is separate and untouched. Scene **Undo** alone can return an object without restoring its retired Citizens binding; use the pre-deletion restore to recover both. Until restored, the slot keeps the first pre-deletion copy, even if the reduced world advances or another object is removed.

Named PC world restore pauses Citizens before loading, blocks its timer and browser autosave while the service exchange is pending, and writes the accepted or rolled-back world after the exchange settles. A delayed rejection regression checks that the staged world never reaches browser storage. At this earlier reservation-lifecycle checkpoint, Operators had to pause Citizens before any scene or game proposal because every resident move advanced the scene revision. The live-revisions candidate above narrows that restriction for finite offline edits to unrelated objects. Its AI, image, voice, and game planning paths remain strict; the demo's autonomous runtime itself does not need a planner request per tick.
