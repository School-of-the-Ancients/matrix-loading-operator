# LLMR ideas for a composable Matrix runtime

Reviewed 2026-09-20 against Microsoft LLMR commit **9d4b72faeee99524220c31df925bcf785b272643**, which was the upstream default-branch HEAD when checked. This extends [LLMR-Voice-Review.md](LLMR-Voice-Review.md). Source inspection is not a Unity compatibility test. The runtime-program design below is **proposed**, not implemented by writing this document. No LLMR code, compiler binaries, or assets were imported.

## Direction

Let the AI compose behavior from reusable Unity capabilities, as it already composes scenes from reusable prefabs. A different request should normally supply a different program or configuration, rather than require a new prefab or application build. Unity can supply procedural transforms, interaction events, animation playback, and physical simulation underneath that program.

The current rotate/bob implementation establishes persistent behavior configuration, stable object targeting, pause/removal, and separation between placed state and decorative animation. It does not yet provide timed sequences, triggers, physics, a general scripting language, or navigation. Those missing capabilities should be named explicitly instead of approximating “bounce when I touch it” with a static transform or unrelated bob loop.

## Immediate adoption and the remaining feedback gap

1. **Implemented: structured runtime skill descriptions.** `ControlService/ai_adapter.py::runtime_skill_catalog` derives `runtimeSkillCatalog` from validated `behaviorKinds`. The shared Planner path supplies the same catalog to Codex and OpenAI-compatible providers. It describes units, defaults, ranges, pause/disable/remove semantics, support-frame meaning, and the placement executor's baseline ownership. Older players receive an empty skill list. Physics, triggers, paths, navigation, runtime code generation, and swept-volume collision are explicitly unsupported. Player-supplied catalog prose is discarded and regenerated by the PC. Four focused tests cover capability filtering, parameter/validator agreement, identical provider context with spoofed catalog removal, and the empty old-player catalog; final suite results belong in the feature validation report.
2. **Proposed: grounded repair context.** Let an explicit retry include the failed request ID, acknowledged results, unresolved commands, and a fresh snapshot. Bound the receipt's size and retain the existing scene/client revision guard and review step. Test partial execution, deleted objects, changed anchors, and stale completions. This repair proposal feedback loop is not implemented in the current feature.

The catalog is context for choosing existing runtime commands; it does not add new behavior primitives. The program interpreter and other recommendations below remain design work.

## Next runtime layer: programs assembled from typed nodes

Implement one small interpreter in the Unity player, with explicit dispatch to compiled Unity functionality. The AI authors data against a published schema. Proposed first program fields are `schemaVersion`, `programId`, `ownerObjectId`, `enabled`, `entry`, and a bounded node collection. References are stable object/anchor IDs or validated child-channel IDs, never arbitrary object-name lookup or reflected method names.

Start with a useful set that composes:

- **Control:** sequence, parallel with explicit completion policy, bounded repeat, delay, and cancellation. Limit nodes, nesting, concurrent branches, execution work per frame, and event frequency.
- **Procedural motion:** timed translate/rotate/scale or validated keyframe curves, with explicit local/anchor/world frame and easing. Existing rotate/bob remain compatible leaf behaviors.
- **Events and conditions:** selected, deliberate controller interaction, timer elapsed, and later verified proximity/contact. Bind and unbind event subscriptions with program lifetime; prevent self-triggering event storms.
- **Appearance:** whitelisted color/material parameters on bundled assets, after an ownership and persistence policy exists.
- **Physics, in a subsequent step:** compiled Rigidbody/collider bindings for bounded mass, gravity, impulse, and constraints. Use Unity's physics engine to produce motion; the AI supplies parameters rather than frame-by-frame poses. Validate compatible colliders and object scale, and prevent simultaneous transform-animation and Rigidbody authority over the same pose.
- **Character actions, later:** animation clip/curve playback, gaze, and navigation via executors that return Running/Succeeded/Failed. GOAP can choose those actions once their execution semantics work; see [GOAP-Next-Step.md](GOAP-Next-Step.md).

For example, “when I select the cube, spin it for two seconds, wait half a second, then float upward” becomes an event connected to a sequence of reusable motion nodes. “Make a pendulum” would eventually compose a body, constraint, and initial impulse. Neither requires a dedicated prefab named after the request. These examples are design targets, not requests the current rotate/bob build can already execute.

Program installation/replacement/removal should pass through the current proposal, command, undo, and persistence path. Validate the whole program before activation. Keep a registry of all owned objects, subscriptions, and physical components so cancellation, deletion, clear, undo, and reload clean up reliably. Save program definitions and deliberately specified persistent state; do not promise exact physics replay or animation phase restoration unless implemented and tested.

Expose program status, active node, completion/failure reason, and a bounded execution trace to the PC and AI. Postconditions should use observed state with tolerances and timeouts. A declaration that an object will reach a destination is not success. Missing anchors stop affected work and produce an explicit failure; there is no world-origin fallback.

## Why this path fits the actual Quest build

Matrix's [QuestBuildSetup.cs](../Assets/Sandbox/Editor/QuestBuildSetup.cs) explicitly sets Android to **IL2CPP** and **ARM64**. LLMR's [README](https://github.com/microsoft/LLMR/blob/9d4b72faeee99524220c31df925bcf785b272643/README.md#L15-L23) identifies tested Unity 2021.3/2022.3 releases and a purchased Roslyn compiler dependency. That evidence does not establish its generated assembly loader works in this Unity 6000.6 Android player.

Unity documents that IL2CPP is ahead-of-time compiled, cannot JIT, and cannot implement `System.Reflection.Emit`. Reflection over existing compiled functionality is distinct from compiling and executing arbitrary new managed methods. Consequently, emitting a new C# DLL on the PC does not make its new methods executable by the current native Quest build. See [Unity's IL2CPP limitations](https://docs.unity3d.com/6000.0/Documentation/Manual/scripting-restrictions.html).

A precompiled interpreter can still execute new program data at runtime. Once the needed nodes/bindings ship, new combinations, parameters, curves, and event connections need no app rebuild. Adding a genuinely new engine binding still requires an application update. Other scripting VMs or hot-update runtimes are separate integration choices that require their own licensing, Android/IL2CPP, lifecycle, and performance validation; none is installed or claimed working here.

## Prioritized proof points

1. Finish the current rotate/bob lifecycle, real-provider, save/load, and wearer checks, preserving white-room and room-aware editing.
2. Use the implemented skill catalog when adding and proving one finite sequence with cancellation and save/load. Reject unknown node types and conflicting pose writers without partial installation.
3. Add one deliberate interaction trigger and verify deletion/undo cancels subscriptions and active work.
4. Add one physical action against actual room collision geometry; verify timeout/failure and supported save semantics before exposing additional physics controls.
5. Add reusable program recipes and compact acknowledged memory. Connect finite character actions and room navigation after their independent acceptance tests.

This borrows LLMR's decomposition, context, skill discovery, inspection, feedback, and runtime authoring ideas while retaining Matrix's working identity, room-placement, review, undo, and PC persistence systems. It does not import LLMR's entire scene or replace working controllers, voice, or provider selection.
