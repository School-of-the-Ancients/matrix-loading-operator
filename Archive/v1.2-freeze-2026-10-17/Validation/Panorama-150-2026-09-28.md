# Issue #150 — Matrix panorama environment validation

This milestone adds a world-level equirectangular panorama to the existing Matrix WebXR scene. The panorama is a registered image dependency, not geometry or a physical-room measurement. This record separates automated checks, a live desktop browser run, and Quest wearer evidence.

- ControlService: `python -m unittest discover -s ControlService -p test_*.py -q` — **868/868 passed**. Focused tests cover PNG validation and digest registration, exact typed action receipts, stale revision and mismatched receipt rejection, the private MCP bridge, HTTP image bytes, and PC checkpoint dependency failure.
- WebRuntime: `npm test` — **660/660 passed**. Focused tests cover set/change/get/remove with stable object IDs, Undo/Redo, browser and PC restoration, browser archives, missing assets, old-world recovery when the panorama catalog fails, AR suppression, checksum/size/dimension preflight, timeout, and late decode cleanup. Delayed-preflight regressions verify that a successful direct edit cannot be overwritten by a queued panorama command or browser checkpoint restore, that stale commands return failed receipts, and that an offline browser restore remains available. XR entry is blocked before native session setup while a world restore is active. AR clear/save/exit and indirect load edits now preserve the panorama contract.

A second Quest review used PR source head `2a4bf35cca1e7addffd2c1a57cbd4add3600a4a8` on a separate `18965` service with the same private panorama catalog and a copy of `panorama-150-final-head-smoke`. A subsequent live VR snapshot retained Azimuth B's full digest and 90° yaw, along with the original block ID `d48322e4eb684a16a35dfd9aa6cfec26`; five additional wall/orb objects had been added to that browser world. The service did not capture an AR snapshot at the moment of the wearer's report, and the wearer did not exercise a panorama change on this Quest run.

The Quest setup exposed a checkpoint-picker bug: the initial authenticated checkpoint-list request could fail before the token was entered, and entering the token refreshed assets but not the PC checkpoint list. The token-change handler now retries the PC checkpoint and legacy scene lists. On `18964`, a fresh desktop page showed the expected pre-authentication recovery wait; entering the token recovered Azimuth B and populated the picker with `panorama-150-final-head-smoke`. A focused review also found that physical-AR **Clear** appeared to remove the panorama from the session, while browser save and desktop return retained it. AR Clear now removes objects while retaining the hidden panorama; AR load/Undo/Redo cannot change it indirectly. Desktop Clear still removes it. The updated WebRuntime passed **659/659** tests and the production Vite build. The wearer check above loaded the page before these final picker and AR consistency fixes were built.

At source head `47375f236119d132f4f7d01af886f2b2ceebc883`, the `18964` desktop review service was restarted with the local Agent/MCP environment and the same isolated scene and panorama catalog. The authenticated Agent session returned `idle`; a fresh browser reload and token entry recovered the one-block world and named PC checkpoint, then **Start or resume Codex** showed `Ready` with reviewed approvals. The Agent inspected the scene and catalog and, after an exact approval, set Azimuth A at 35°: request `af798e36543c461c81b547e66d728938` returned a successful `environment-set` browser receipt. A second exact approval restored Azimuth B at 90°: request `a9cae221cf324486b5a05c820ef581bc` likewise returned a successful `environment-set` receipt. The browser displayed each panorama label. The final service snapshot retained only block `d48322e4eb684a16a35dfd9aa6cfec26` at position `(0, 0, -2)`, zero rotation, and unit scale, with Azimuth B's full digest and 90° yaw. No file or scene-object edits were requested. This establishes a current-head Agent-driven desktop sample change and restoration; the page has no direct panorama selector, and the prior Quest wearer check did not exercise this change.

After that source-head desktop review, the browser exchange was bounded to one panorama dependency preflight per exchange. A slow fetch or decode can consume most of the PC runtime's 15-second lease; serially preflighting two panorama commands in one exchange had delayed the first receipt and the next heartbeat. The browser now records the first command's exact receipt and leaves subsequent commands for the next exchange, where the PC can acknowledge that result before another panorama preflight starts. The existing in-flight exchange guard and queued command order remain in place. The new deferred two-command regression, the full **660/660** WebRuntime tests, and the production Vite build passed. This later fix has **no Quest wearer result**; the VR/AR observations above belong to earlier review builds.

The source release builder includes this contract documentation and compiled Web runtime. Its default public package does not include the private panorama catalog, browser storage, or PC checkpoints. The final v1.0 frozen-package gate in #152 still needs an explicitly reviewed panorama and matching isolated data, plus its own exact-package Quest VR/AR observations.
